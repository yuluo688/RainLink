# 架构评估与优化 · 2026-10-15

当前结构适合作为桌面优先的 M0 基础框架。领域模型、数据库和平台接口已有清晰边界；主要问题在异步顺序、进程生命周期与订阅粒度。节点、网络核心和遥测尚未实现，因此本次评估不包含真实代理吞吐量、海量日志或五平台运行性能。

## 评价与已完成改进

| 维度 | 原有情况 | 本次改进 |
| --- | --- | --- |
| 架构 | 领域层独立，但全局 providers 同时装配数据库、平台适配器和业务状态 | 新增 application 层；界面只访问用例状态与领域接口，具体实现集中在 `app/dependencies.dart` 注入 |
| 语法与类型 | Dart 3.6 的接口、不可变对象、枚举和 switch 使用合理，Go 包结构简洁；宿主结果使用异构 Future 列表及位置转换 | 使用明确的 `HostCommandResult`；独立协议解析并校验字段类型、非空值和显式 null；`ConnectionSessionState` 避免与 Flutter 同名类型冲突 |
| 时间复杂度 | 当前没有嵌套大规模遍历；并发 K 次检查会重复启动 K 个进程、读取并解析 K 份相同状态 | 同一 Gateway 合并进行中的检查，完成后仍可重新刷新；单次读取解析保持 O(B) |
| 代码耦合 | 页面引用全局装配入口；Desktop 继承 Unavailable 具体实现，进程执行与 JSON 解析混合 | 接口、进程执行、协议解码分离；Desktop 直接实现 CoreGateway，拒绝未接入的连接命令 |
| 性能与可靠性 | 主题写入期间的后续请求被静默丢弃；超限可能等到超时才失败；概览订阅触发整页构建 | 主题串行持久化并传播各次错误；宿主尽早失败并等待退出；局部订阅、复用主题和快捷键映射，窄屏不再预建桌面设置列表 |

### 异步行为修复

主题原来的 `_saving` 门禁会丢请求：初始深色 → 请求浅色（写入中）→ 请求深色，最后错误地停在浅色。现按请求顺序写入，只在成功后更新内存状态，执行请求时再判断是否与当前值相同。一次失败不会阻塞后续请求；Controller 销毁后不再更新状态或执行排队写入。已经开始的 SQLite 写入无法通过当前仓库接口撤销。

宿主执行预算包含进程启动和输出读取，默认 5 秒；stdout/stderr 各限 64 KiB，stderr 只计数并排空。失败时立即取消流并终止直接子进程，最多另等 1 秒确认退出，回收失败会明确报错。操作系统的 `Process.start` 不可取消；若超时后才取得句柄，会在取得时终止晚到进程。当前宿主不创建后代进程。

`FutureProvider` 原本已经缓存宿主状态，之前并非每帧都启动进程。本次合并解决的是显式并发检查与刷新交叠；未来持续遥测仍需会话 IPC。

### 依赖方向

```text
presentation → application → domain
data、platform → domain
app/dependencies.dart → 选择、注入并管理具体适配器
```

领域层仍不依赖 Flutter、Riverpod、SQLite 或操作系统。连接目标与活动快照继续分离，未接入的连接、系统代理和 TUN 能力保持关闭。

## 复杂度与资源边界

B 为一次命令的输出总字节数，K 为同时检查的调用数，P 为偏好记录数，D 为导航项数，V 为整页控件量，Q 为主题请求数。

| 操作 | 修改前 | 修改后 | 说明 |
| --- | --- | --- | --- |
| 单次宿主读取与解析 | 时间 O(B)，空间 O(B) | 时间 O(B)，空间 O(B) | BytesBuilder 减少字节保存与复制常数，不改变复杂度阶数 |
| K 次并发宿主检查 | K 个进程，累计读取/解析工作量 O(KB)，输出空间 O(KB) | 1 个进程，累计工作量 O(B+K)，含调用者等待结构的空间 O(B+K) | 仅合并同一 Gateway 中进行中的工作，不永久缓存结果 |
| 主题读写 | 主键查询/更新约 O(log P)，并发请求可能丢失 | 单次仍约 O(log P)，Q 次有序请求最坏 O(Q log P) | SQLite 已有主键索引和后台 isolate，无需再加内存缓存 |
| 代理模式/宿主提示更新 | 概览 build 范围 O(V) | 限于对应卡片或提示控件 | 不承诺 Flutter 布局、绘制或帧率按同样比例改善 |
| 导航匹配 | O(D)，当前 D=8 | 保持 O(D) | 固定小集合无需改为哈希表；快捷键表改为一次创建 |
| Go status | 固定字段，O(1) 时间与空间 | 保持 O(1) | 当前没有业务循环或共享并发数据，不额外引入 goroutine/缓存 |

固定浅色、深色 ThemeData 各构建一次并复用；切换主题仍会触发 Flutter 必要的主题更新。总体上，当前优先优化 I/O 生命周期与重建范围，没有证据支持增加更多状态框架、后台服务或通用抽象。

上述复杂度描述输入规模和累计工作，不等于并发请求的实际延迟；进程启动还有操作系统调度、加载与管道成本。

## 本机测量

Windows x64，Dart 3.6.2 JIT，Go 1.25.5，使用相同 M0 宿主二进制。排除 Dart VM 启动，先预热 5 次，再对每个并发度采样 30 批；记录整批完成耗时。

| 请求负载 | 改前 p50 / p95 | 改后 p50 / p95 |
| --- | --- | --- |
| 单请求 | 20.505 / 28.656 ms | 19.702 / 20.763 ms |
| 同时 8 请求 | 51.353 / 67.318 ms | 19.723 / 20.537 ms |

这是非隔离的本机观察，改前采样与一次 Flutter 测试加载有重叠，不能据此推导稳定提升百分比或实际网络性能。确定的资源收益是同批 8 次检查由 8 个进程减为 1 个，另有可控测试验证启动次数。数据保存在 [architecture-metrics.json](verification/architecture-metrics.json)。

## try/catch 与条件分支复查

- 协议校验改为 Map 模式匹配；只有 `jsonDecode` 的语法错误需要捕获，字段不合法直接抛出领域异常，移除人为抛出再捕获的 FormatException 与类型强转。
- 设置页仅捕获可恢复的 Exception，程序 Error 继续向上传播；通知移至 try 外，避免把界面错误误报为保存失败。生命周期取消使用明确的 ThemeUpdateCancelled，保存状态仍由 finally 恢复。
- 启动阶段保留顶层 Object 捕获作为失败界面的边界，先记录原始错误；数据库关闭再失败时单独报告，不覆盖原异常与堆栈。
- 进程取消只发出取消信号，由统一清理流程终止进程，删除重复 kill。主题队列保留内部错误恢复，但调用者仍收到原操作的错误。
- 保留重复点击、相同主题、await 后销毁检查、输出限额和布局断点等有明确语义的 if；不通过增加闭包或复杂表达式来机械减少分支数量。

新增测试覆盖保存异常后的重试、程序 Error 不被吞掉、启动及清理同时失败；现有进程测试增加仅终止一次的断言。程序 Error 回归已先在旧实现复现失败，修改后通过。
